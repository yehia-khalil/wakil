A request built of parts

2c-iv · issue #179 · the resolveDraft seam

In the API client pane a request field is a sequence of parts — a literal, a named hole, or a bound value taken from a grid on screen. There is no delimiter anywhere, so a database cell containing {{ or ../ is inert by construction rather than by escaping. A live bound value is re-read at send by its row's key values; a captured one holds what it was given and dies with the rows it came from. One pure function turns the draft into a wire request, or into one refusal naming every failure.

This page exists to answer one question: does that model hold up when you push it through the cases that are hard to reason about on paper? Press buttons. Watch the state. The interesting moment is when you think “wait, that shouldn't be possible”.
